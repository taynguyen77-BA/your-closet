# Wardro V2.2.0 — Wardrobe Intelligence Foundation

V2.2.0 makes the existing Wardrobe Item structured, searchable, filterable, and ready for future intelligence. It does not add AI search, vector search, outfit generation, virtual try-on, Firebase, payment, marketplace, or infrastructure services.

|---|---|---|

| Subcategory | Missing from the shared item contract | Optional additive field; no inference without source data |

## Provider-neutral model

The additive `intelligence` object is a domain contract, not a Firebase or JSON-persistence schema. It is written by the authoritative wardrobe API and can be derived at read time for legacy rows that do not yet contain the field.

```ts
interface WardrobeIntelligence {
  schemaVersion: 1;
  category: IntelligenceValue;
  subcategory?: IntelligenceValue;
  colors: IntelligenceValue[];
  pattern?: IntelligenceValue;
  material?: IntelligenceValue;
  style?: IntelligenceValue;
  seasons: IntelligenceValue[];
  occasions: IntelligenceValue[];
  brand?: IntelligenceValue;
  size?: IntelligenceValue;
  status: 'active' | 'archived';
  source: 'user' | 'ai' | 'mixed';
  confidence?: number;
}

interface IntelligenceValue {
  raw: string;
  normalized: string;
  display: string;
}
```

The model is backward-compatible. Existing fields are not removed, existing CRUD paths are not renamed, and existing stored records do not require a destructive migration.

## Metadata normalization

Normalization is deterministic and testable. Each value keeps the source `raw` value, a stable lower-case `normalized` value, and a user-facing `display` value. Controlled aliases are deliberately narrow: `tee`, `t-shirt`, and `shirt` map to the existing `top` category; `grey` maps to `gray`; `fall` maps to `autumn`. `cream` and `off-white` remain distinct values because they carry different product meaning without stronger evidence.

The normalizer does not use AI, does not merge arbitrary values, and does not delete raw values. Vietnamese search text is accent-insensitive for matching while stored display values remain unchanged.

## Smart Closet query contract

The collection read contract is:

```text
GET /api/wardrobe/items
```

Supported query parameters are:

| Parameter | Accepted behavior |
|---|---|
| `category` | Exact normalized category match |
| `subcategory` | Exact normalized subcategory match when present |
| `color` | Exact normalized color match against any color |
| `style` | Exact normalized style match |
| `season` | Match any normalized season |
| `occasion` | Match any normalized occasion |
| `search` | Deterministic text matching over name, type, tags, color, style, material, and normalized metadata |
| `status` | `active` or `archived`; legacy records read as active |
| `sort` | `newest`, `oldest`, `name_asc`, `name_desc`, `wear_count_desc`, `wear_count_asc` |
| `limit` | Integer from 1 through 50; default 24 |
| `cursor` | Non-negative numeric offset returned by the previous response |

The response preserves the standard API envelope and adds deterministic metadata in `meta.facets`:

```json
{
  "data": [],
  "meta": {
    "total": 0,
    "limit": 24,
    "cursor": null,
    "facets": {
      "categories": [],
      "colors": []
    }
  }
}
```

The current implementation filters the authenticated user’s server-owned rows and never accepts a client `userId` for collection ownership. In Manus mode, filtering is performed by the Manus provider boundary. In Firebase mode, the same domain query function is applied to owner-scoped Firestore rows, preserving future provider compatibility without introducing a Firebase-specific model.

## API and migration behavior

The existing upload and single-item CRUD endpoints remain unchanged. `POST /api/wardrobe/items` writes the additive intelligence object from validated legacy and optional fields. `PATCH /api/wardrobe/items/:id` accepts the additive metadata fields and regenerates intelligence from the merged item. Image references, user ownership, and Storage paths remain immutable through PATCH.

No standalone data migration was created. That is intentional: the model is additive, new records are normalized at write time, and legacy records are normalized at query time. If a future backfill is required for production scale, it should be a separate backward-compatible migration with dry-run, rollback, and provider-specific operational approval.

## Frontend behavior

The existing Closet screen now uses the authoritative query endpoint in live mode. It displays the server-reported total, color facets, active filter count, current sort label, a clear-filter action, and a no-results explanation. The existing design language and grid/list toggle remain intact. Favorites and rarely-worn views remain local presentation filters over the server result; no redesign or AI stylist surface was added.

## Security

All query operations are authenticated and server-owned. User B cannot query User A’s items through filters because the server scopes the source rows to the derived identity before filtering. Invalid sort, status, limit, cursor, and control-character inputs are rejected. The existing 404/403 semantics for item and image access, upload bounds, idempotency, and AI quota ledger remain unchanged.

## Runtime providers

The current runtime remains `WARDRO_RUNTIME_MODE=manus`. The Manus data provider remains a small server-side development adapter and is not expanded into a production database. The normalization and query modules are provider-neutral. Firebase remains a future provider option behind the existing runtime boundary; no Firebase project, migration, or credential is introduced by V2.2.0.

## Explicitly future

AI search, semantic/vector search, automated taxonomy learning, outfit generation, AI stylist, virtual try-on, marketplace, payment, community redesign, weather, notifications, cloud storage, and production-grade database infrastructure remain future work.
