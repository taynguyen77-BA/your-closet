# Wardro V2.1.2 — Core Wardrobe Production Chain

## Scope

V2.1.2 keeps the existing mobile review UX and moves the production wardrobe write path behind dedicated authenticated APIs. It does not implement payment, marketplace settlement, weather providers, virtual try-on production, or a UI redesign.

## Runtime flow

`Mobile image selection → POST /api/wardrobe/upload → Firebase Storage → existing authenticated clothing detection AI route → review draft → POST /api/wardrobe/items → Firestore clothes document → wardrobe list/detail`

The upload API derives the owner UID from the verified Firebase token. It accepts only JPEG, PNG, and WebP images, enforces the existing 10 MB boundary, checks image signatures, rejects malformed multipart input, and generates the Storage object path server-side under `users/{uid}/clothes/`.

The mobile review draft retains the server-issued URL/path and a transient local source URI. Confirming a draft reuses the validated upload rather than uploading the same image a second time. The draft remains separate from the persisted `clothes` document until the user confirms.

## Persistence and idempotency

`POST /api/wardrobe/items` requires `Idempotency-Key`. It resolves the owner from Firebase Auth, validates all persisted fields, verifies the Storage URL/path, checks the user plan-derived closet limit, and atomically creates the `clothes` record, request record, and user count update in one Firestore transaction. Repeating the same key returns the original item and does not increment the count again.

The dedicated item `GET`, `PATCH`, and `DELETE` routes enforce owner isolation. PATCH is metadata-only; image-reference replacement is intentionally not supported by the generic path. DELETE atomically removes the Firestore item and decrements the count, records a retriable `storage_cleanup_tasks` marker, and then attempts to remove owned Storage objects. A successful cleanup transitions the marker to `completed`; a failed cleanup remains `pending` with a safe error code. This avoids an uncontrolled orphan without adding a background job system.

The legacy generic `/api/resources/clothes` create/update/delete operations are blocked with `USE_WARDROBE_API`, so unvalidated generic writes cannot bypass the dedicated boundary. Reads remain available for compatibility.

## Account deletion

Account deletion removes `users/{uid}/clothes/` Storage objects before cascading user-owned Firestore data and deleting the Firebase Auth identity. If Storage cleanup fails, deletion stops before Firestore/Auth deletion. AI usage/audit retention is not changed because no approved product/legal retention policy is present; this remains a product/legal decision.

## Validation commands

From the repository root:

```bash
cd admin && npm run lint
cd admin && npm run typecheck
cd admin && npm test -- --runInBand
cd admin && npm run build
cd mobile && npm run typecheck
cd mobile && npm test -- --runInBand
cd tests/rules && npx --yes firebase-tools@13.31.2 emulators:exec --project demo-your-closet --only firestore,storage "npm test"
```

The CI workflow runs the Firestore and Storage rules suites through an isolated emulator lifecycle, while migration tests remain on a separate isolated Firestore-only lifecycle. Account deletion is additionally verified against isolated Auth, Firestore, and Storage emulators with `admin/jest.integration.config.js`; the test covers owned-data deletion and fail-closed Storage failure ordering.

The canonical production API name is `/api/wardrobe/*`. Historical `/api/closet/*` references should not be used for new consumers. A narrow admin dependency hardening was also applied: Next.js is pinned to `15.5.23`, and patched transitive versions are enforced for `form-data`, `nanoid`, and `websocket-driver`; broad dependency modernization remains out of scope.
