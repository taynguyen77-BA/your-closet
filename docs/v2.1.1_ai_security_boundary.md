# Wardro V2.1.1 — AI Security Boundary

## Scope

V2.1.1 hardens the existing Next.js/Firebase AI path without changing product UX, provider architecture, payment, marketplace, or production data. The trusted server derives identity and plan from Firebase Auth and the `users` document. The mobile client supplies only the logical request identifier and operation payload.

## Protected operations

The server accepts only these explicit operations:

| Operation | Route | Input |
|---|---|---|
| `clothing_detection` | `/api/ai/clothing/detect` | `multipart/form-data`, image |
| `clothing_enhance` | `/api/ai/clothing/analyze-and-enhance` | `multipart/form-data`, image |
| `outfit_recommend` | `/api/ai/outfits/recommend` | JSON with `wardrobe` and `weather` |
| `virtual_tryon` | `/api/ai/try-on/generate` | multipart image, item IDs and scene |
| `style_profile_analyze` | `/api/ai/style-profile/analyze` | JSON with `wardrobe` |

Unknown paths, arbitrary upstream paths, non-POST methods and unsupported fields are rejected before quota reservation or provider invocation.

## Authentication and plan authority

Every protected operation requires a Firebase ID token in the `Authorization: Bearer` header. The server derives the user ID from the verified token and reads the current plan/status from the server-side `users/{uid}` document. Request-body identity, plan, quota, and billing fields are not trusted.

Suspended users and users without a server profile are rejected. Demo mode uses the existing mobile mock provider and does not create production quota records.

## Request and provider limits

Image requests use multipart form data and are limited to 10 MB with an image MIME type. JSON requests are limited to 256 KB. Operation-specific required fields are validated before reservation. Provider requests and response-body reads are bounded by a 20-second timeout, and the complete logical operation is bounded by a 45-second deadline across the primary/fallback sequence. Provider responses are size-limited and JSON responses are parsed and validated before commit.

The mobile provider sends one `Idempotency-Key` and `X-Request-Id` per logical AI call and reuses them across its bounded network retries.

## Quota ledger

The server stores one deterministic `ai_usage/{sha256(userId:idempotencyKey)}` document per logical operation. A Firestore transaction atomically reads the user and usage document, rejects duplicate active requests, verifies available free-plan quota, creates a `RESERVED` record, and decrements the server-side remaining quota.

The state machine is:

```text
RESERVED → COMMITTED   valid non-fallback provider result
RESERVED → RELEASED    provider failure, timeout, invalid response, or fallback result
```

A committed or released record cannot be transitioned again. Released free-plan reservations restore quota only when the reservation and current user record belong to the same quota period. Pro and Premium remain unlimited according to the existing `-1` plan contract.

A completed idempotent request returns its stored response when it is within the replay-size bound. A request that is still `RESERVED` returns an in-progress conflict rather than reserving again. A failed request without a replayable result requires a new idempotency key.

## Authoritative logging

The trusted server writes one `ai_logs/{usageId}` document during the same finalization transaction. It records operation, user, plan, provider, model, fallback flag, quota units, status, result status, idempotency key, request ID and timestamps. Provider cost is recorded as `NOT_OBSERVABLE`; no token count or currency cost is fabricated.

The generic resource API rejects client creation of `ai_logs`, and Firestore rules deny direct client create/update/delete for `ai_logs`. Admin SDK writes remain available to the trusted server, and existing owner/admin reads remain available.
