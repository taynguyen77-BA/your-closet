## 1. Project Overview

### 1.1 Purpose

This BRD v2.0 formalizes the requirements for **Wardro** (product codename "Your Closet" in the codebase; final consumer brand name still pending trademark resolution — see Open Item OI-1), a B2C AI-powered fashion mobile app positioned as a **Personal Fashion Operating System**.

1.1.1 This version's primary purpose is to **reconcile the written specification with the already-implemented codebase**, so that BRD, User Stories, and Acceptance Criteria accurately describe what will ship, rather than a narrower MVP that the engineering team has already exceeded.

1.1.2 Key platform capabilities in scope for this version:
1.1.2.1 Account & Identity (Phone OTP, Google, Facebook — no Email/Password)
1.1.2.2 AI Closet (upload, AI detection, AI image enhancement, manual correction)
1.1.2.3 Home Dashboard (weather-aware outfit suggestions, community & shopping banners)
1.1.2.4 Outfit Generator & Outfit Library (save, favorite, hide, wear-count tracking)
1.1.2.5 **Virtual Try-On** (scene-based AI image generation) — promoted from Phase 2 to MVP
1.1.2.6 Event Planner (event-linked outfit suggestions)
1.1.2.7 **Community / Marketplace** ("Pass đồ" — listings, trade offers, messaging, moderation) — promoted from Phase 2 to MVP
1.1.2.8 AI Shopping Assistant & Affiliate tracking
1.1.2.9 Style Profile (Quick Quiz) & **Advanced Style Preferences** (body measurements, sizing, budget) — full MVP, feeds AI Stylist prompts
1.1.2.10 Membership & Tiering (**Free / Pro / Premium**) with **AI Model Tiering & Routing**
1.1.2.11 Payment & Billing (VNPay, MoMo prioritized; Apple Pay/Google Pay Phase 1.1)
1.1.2.12 Missions & Rewards (Admin-configurable campaigns)
1.1.2.13 Notifications
1.1.2.14 Guest / Public Browsing Mode
1.1.2.15 Admin CMS (Users, RBAC Admin Users, Membership, Missions, Community Moderation, Notifications, CMS Content, Trends, Affiliate, Transactions, Payments, Security & Audit, Support Tickets, Outfits, Analytics Dashboard)
1.1.2.16 Fashion Knowledge Base & Weekly Trend Monitoring Job

1.1.3 Explicitly in scope for this phase (all items above); explicitly out of scope: see Section 1.4 and inherited Out-of-Scope list from Product Vision v2.0 (B2B Merchant Suite, escrow/secured payment for C2C, IoT smart closet, multi-language/international expansion, sale of personally-identifiable data).

### 1.2 Pre-requisites

1.2.1 Firebase project provisioned with Authentication (Phone, Google, Facebook providers only — Email/Password provider must be **disabled**, not merely hidden from UI, per PO decision to remove rather than feature-flag).
1.2.2 Firestore + Storage + Cloud Messaging enabled; security rules deployed per `firebase/firestore.rules` and `firebase/storage.rules`.
1.2.3 Backend AI proxy (Next.js API routes under `admin/`) configured with `AI_API_BASE_URL`, `AI_PROVIDER`, `GEMINI_API_KEY` (or equivalent) — server-side only, never exposed to mobile client.
1.2.4 VNPay and MoMo merchant accounts provisioned and sandbox-tested before Payment & Billing (3.14) goes live; Apple Pay/Google Pay merchant setup deferred to Phase 1.1.
1.2.5 AI Model Routing configuration (Section 4.2) must exist in `admin_settings` before Membership tiering (3.4) can differentiate AI quality by tier.
1.2.6 Weekly Trend Monitoring Job scheduler (cron, weekly cadence — confirmed unchanged from v1.5) must be deployed on the backend hosting the AI proxy.

### 1.3 Assumptions

1.3.1 The existing codebase's Firestore collections (`users`, `clothes`, `outfits`, `events`, `trends`, `missions`, `plan_limits`, `user_missions`, `listings`, `transactions`, `subscriptions`, `notification_templates`, `notifications`, `affiliate_products`, `support_tickets`, `ai_logs`, `cms_content`, `admin_settings`, `adminUsers`, `marketplace_messages`, `trade_offers`, `listing_reports`, `shopping_events`) are the authoritative data model going forward; new requirements build on this schema rather than replacing it.
1.3.2 The membership plan value in the database will be **rebuilt** from `'free' | 'premium' | 'elite'` to `'free' | 'pro' | 'premium'` — this is a breaking schema change requiring a migration task, not a display-label-only change (per PO decision D2).
1.3.3 Email/Password authentication code currently present in the mobile app will be **removed** (not feature-flagged) in a follow-up engineering task; this BRD specifies the target state (3 providers) as the requirement.
1.3.4 The AI provider backend (external to the reviewed codebase) is assumed to support model selection per request (i.e., the proxy can choose which underlying model to call based on tier + feature), since no routing logic exists yet in the reviewed repo.
1.3.5 "Pro" and "Premium" tier AI model upgrades are assumed technically and commercially viable from day one of MVP launch (no gate/threshold required before upgrading paid tiers — unlike the original Free-tier-only "prove-it-first" model gate).
1.3.6 *(NEW — v2.2)* `clothing_enhance` (image standardization) is not latency-sensitive and is assumed to route through the AI provider's Batch API by default (≈50% cost discount, 24hr async window), showing a "processing" state to the user rather than a live-wait spinner. `virtual_tryon` is assumed to remain synchronous/real-time (Batch API is not viable there) to meet the 15–20s generation target in Section 7.

## 2. Process Flows

**Legend:** 🟢 Happy Path · 🔴 Exception/Error Path · ▶ Start · ⏹ End – Success

### 2.1 Registration & Login

▶ Start: User opens app (first launch or returning)
🟢 Splash checks Firebase config, local onboarding flag, Firebase Auth session, biometric preference.
🟢 New user → Onboarding slides → Auth Welcome screen → chooses **Phone OTP**, **Google**, or **Facebook**.
  - Phone OTP: enters number → reCAPTCHA (web) or native verification → enters OTP code → YES valid → account created/linked → NO invalid → 🔴 error "Mã OTP không đúng, thử lại" (max 3 attempts, then cooldown).
  - Google / Facebook: Expo AuthSession (native) or Firebase popup (web) → provider consent → YES granted → Firebase sign-in with provider credential → NO denied/cancelled → 🔴 return to Auth Welcome, no error toast (user-cancelled is not an error state).
🟢 First successful login/register → check `hasCompletedStyleSurvey`/`styleSurveySkipped` → NO → route to Style Survey (initial mode) → YES → route to Home tab.
🟢 Returning user → Firebase session valid → update `users/{uid}.lastLoginAt` → route to Home tab (skip onboarding).
🔴 Session invalid/expired → route to Auth Welcome, preserve `onboardingCompleted=true` so onboarding slides are not re-shown.
⏹ End: User lands on Home tab, authenticated.

**Guest path (2.1b):** User taps "Continue as guest" on Auth Welcome → `isPublicViewer=true` → can browse public-readable data (plans, trends, affiliate products, approved listings) → any write action or private-data read triggers `GuestAuthModal` prompting sign-in → ⏹ End: user either authenticates (joins 2.1 happy path) or dismisses and continues browsing public content only.

### 2.2 AI Closet Core Flow

▶ Start: User taps "Add item" in Closet tab
🟢 Chooses camera or album; bulk album selection capped at 5 photos, picker blocks further selection past 5 with message "Bạn chỉ có thể chọn tối đa 5 ảnh cho mỗi lần upload."
🟢 Photo(s) uploaded to Firebase Storage → backend `POST /api/ai/clothing/detect` called (model per AI Routing Table, Section 9, keyed by user's tier) → returns category/color/material/style/tags + `suggestedName`.
🟢 In parallel or on-demand, user may request `POST /api/ai/clothing/analyze-and-enhance` → returns `enhancedImageCandidates[]` + `qualityWarnings[]` → user picks preferred image (original or enhanced).
🔴 AI call timeout/failure → retry automatically up to 3 times → still fails → show processing/error message, do NOT silently fall back to mock output (unless `EXPO_PUBLIC_DEMO_MODE=true`).
🟢 User reviews AI-suggested tags on `ClothingReviewDraft` screen → corrects any incorrect field → confirms.
🔴 Free tier user at closet item limit → block save, show upgrade prompt (does not discard the uploaded photo from the review draft, so the user does not lose their upload if they decide to delete an old item and retry).
🟢 Item saved to `clothes` collection with `aiConfidenceScore`, `aiQualityWarnings`, `aiMetadata`.
⏹ End: Item appears in Closet grid/list; wardrobe graph updated.

### 2.3 Outfit Generation & Virtual Try-On Flow

▶ Start: User opens Home tab or taps "Refresh suggestions"
🟢 System gathers weather, wardrobe, style preferences (basic + advanced), saved outfits, active events, community listings, affiliate products → calls `POST /api/ai/outfits/recommend` (model per tier) → returns ranked `OutfitRecommendation[]` with `aiExplanation`, `matchingScore`, `missingItems`, shopping/community suggestions.
🟢 User selects a recommendation → "Try it on" → Virtual Try-On screen.
🟢 User uploads/selects their photo, picks a scene (beach/mountain/urban/party/casual/office).
🔴 Free tier: system checks monthly try-on quota (**2/calendar month, resets on the 1st**) → IF exhausted AND no mission-earned bonus available → show "Bạn đã dùng hết lượt thử đồ miễn phí tháng này. Hoàn thành nhiệm vụ để nhận thêm lượt, hoặc nâng cấp Pro." → block generation.
🟢 IF quota available → `consumeAiTry()` → call `POST /api/ai/try-on/generate` (model per tier, per Section 9) → returns generated image.
🔴 Generation fails/times out → do not consume quota; show retry option.
🟢 User saves/shares result; optionally saves the outfit to Outfit Library.
⏹ End: Try-on image displayed, optionally shared outside the app (Sharing API) or saved to device (MediaLibrary).

### 2.4 Community / Marketplace Flow ("Pass đồ")

▶ Start: User taps "Đăng tin" in Community tab
🟢 Selects a closet item, sets `listingType` (sale/trade/giveaway), price (if sale), condition, description, photos, location → submits → listing created with `status=pending_review`.
🟢 Admin reviews in Admin > Community Moderation → YES approve → `status=approved`, becomes publicly browsable (including to guests) → NO reject → `status=rejected` with `moderationNote`, seller notified.
🟢 Buyer browses approved listings → sends message (`marketplace_messages`) or trade offer (`trade_offers`) → seller responds.
🟢 Sale completes → `transactions` record created with `platformFeePercentage`/`platformFee` computed → status progresses `pending → paid → shipped → handed_over → completed`.
🔴 Buyer or seller reports a listing → `listing_reports` created with `status=open` → Admin reviews in Moderation → `reviewing → resolved/dismissed`.
🔴 No escrow in this phase (Phase 2 deferred per PO decision) — system does not hold funds; payment/handover coordination happens outside the guaranteed-settlement flow, and this limitation must be clearly disclosed in-app before a user's first listing/purchase.
⏹ End: Transaction marked `completed`, or listing cancelled/rejected/reported-resolved.

### 2.5 Membership Upgrade & AI Model Routing Flow

▶ Start: User views Membership screen (tier comparison: Free / Pro / Premium)
🟢 Selects target tier → Payment screen → chooses VNPay or MoMo (priority methods) → `payment/prepare` assembles order → redirects to payment provider.
🟢 Payment provider callback confirms success → `subscriptions` record created/updated, `users/{uid}.plan` updated to `pro` or `premium`, quota fields (`aiUsageMonthlyLimit`, `closetItemLimit`) updated per new tier.
🔴 Payment fails/cancelled → no plan change, user returned to Membership screen with a clear failure message, no partial state.
🟢 **From this point forward, every AI call for this user resolves its model via the AI Model Routing Table (Section 9), keyed on (feature, tier)** — e.g., a Premium user's `outfits/recommend` call now routes to the Premium-tier model, not Free's.
🔴 Subscription expires without renewal → auto-downgrade to Free (never an intermediate tier) → AI Model Routing immediately reverts to Free-tier models on the next call → existing closet items retained (not deleted), new uploads blocked if over Free's item limit.
⏹ End: User's tier and AI model quality are both updated consistently across every AI-touching feature.

### 2.6 Admin Moderation & AI Cost Monitoring Flow

▶ Start: Admin logs into Admin CMS (RBAC-gated)
🟢 Views Analytics Dashboard (total/active users, membership conversion %, daily AI usage).
🟢 Views AI system page (`ai_logs`): per-call `modelUsed`, `processingMs`, `status`, `errorMessage`.
🔴 Cost-per-tier trending above threshold → Admin adjusts AI Model Routing config in `admin_settings` (e.g., temporarily route Free tier to a cheaper model) without requiring an app release.
🟢 Admin moderates Community listings/reports, manages Missions, CMS Content, Trends, Affiliate products, Transactions, Payments, Support tickets, Security/Audit logs — all via the generic `AdminCollectionPage` pattern already implemented.
⏹ End: Admin actions logged to `admin_logs` for audit trail (Security & Audit page).

## 3. Detailed Requirements

All functional requirements in this section conform to the Non-Functional Requirements in Section 7.

### 3.1 Account & Identity Management

3.1.1 The system will support account registration and login via exactly three channels: **Phone OTP, Google, and Facebook**.
&nbsp;&nbsp;3.1.1.1 The system will NOT offer Email/Password as a registration or login method. Any Email/Password code paths present in the current codebase will be removed as a follow-up engineering task; this is a specification decision, not a code audit finding.
&nbsp;&nbsp;3.1.1.2 Phone OTP will use Firebase reCAPTCHA verification on web and native Firebase phone verification (or a backend OTP bridge) on native platforms.
&nbsp;&nbsp;3.1.1.3 On OTP failure, the user will have the option to retry up to 3 times before a **60-second cooldown** is enforced before the next OTP request can be sent.
3.1.2 The system will prevent duplicate account creation when a phone number or provider identity already maps to an existing `users/{uid}` record — the existing account will be signed into instead of a new one created.
3.1.3 The system will support Guest / Public Browsing Mode (see Section 3.16) as an alternative to immediate registration.
3.1.4 After first successful login/registration, the system will check `hasCompletedStyleSurvey` and `styleSurveySkipped`; if both are false, the user will be routed to the initial Style Survey (Section 3.13) before reaching Home.
3.1.5 The user will have the option to enable biometric login (Face ID/fingerprint) as a local convenience layer on top of the Firebase session; this preference is stored locally and is not itself an authentication provider.
3.1.6 The user will have the option to log out, which clears local session tokens and the secure biometric preference, but retains the local `onboardingCompleted` flag so onboarding slides are not re-shown on next login.
3.1.7 The user will have the option to permanently delete their account.
&nbsp;&nbsp;3.1.7.1 Deletion will require re-authentication (OTP or provider re-consent) before proceeding.
&nbsp;&nbsp;3.1.7.2 Deletion will remove all personal data across `clothes`, `outfits`, `events`, `user_missions`, `notifications`, `listings` owned by the user, `marketplace_messages`, and `subscriptions`, except data already anonymized/aggregated for internal statistics (per Nghị định 13/2023 compliance).
&nbsp;&nbsp;3.1.7.3 The system will display an explicit, irreversible-action confirmation warning before deletion executes.
3.1.8 Profile editing: the user will have the option to edit `displayName` and `avatarUrl` directly from Profile. Plan, quota, payment, and moderation-related fields will NOT be user-editable — these are protected by Firestore rules and only changed via backend/admin logic.

### 3.2 AI Closet (Wardrobe Digitization)

3.2.1 The user will have the option to upload clothing photos via camera capture, single album selection, or bulk album selection.
&nbsp;&nbsp;3.2.1.1 Bulk upload will allow a maximum of 5 photos per batch; the photo picker will block further selection past 5 and display: "Bạn chỉ có thể chọn tối đa 5 ảnh cho mỗi lần upload."
&nbsp;&nbsp;3.2.1.2 Only image formats will be accepted; video upload is out of scope.
3.2.2 The system will automatically detect category, color, material, style, season, and tags for each uploaded item via the AI Model Routing Table (Section 9), keyed to the user's current tier.
&nbsp;&nbsp;3.2.2.1 Items with a confidence score below the configured threshold [TBD — OI-3] will be flagged "needs review" and prioritized in the user's review queue.
&nbsp;&nbsp;3.2.2.2 On AI call failure or timeout, the system will retry automatically up to 3 times before showing a processing/error message. The system will NOT silently substitute mock output in production.
3.2.3 The system will offer AI image enhancement as a distinct step: `analyze-and-enhance` will return one or more `enhancedImageCandidates` plus `qualityWarnings`, and the user will have the option to select either the original or an enhanced image as the item's primary image.
&nbsp;&nbsp;3.2.3.1 The number of enhancement candidates offered will vary by tier per the AI Model Routing Table (Free: 1 candidate; Pro: 2–3; Premium: 3+).
3.2.4 The user will have the option to correct any AI-suggested tag (type, color, material, style, season, tags, name) before or after saving an item.
3.2.5 The user will have the option to manage closet items: view (grid/list), filter, view item detail, mark as favorite, edit, and delete.
3.2.6 The system will enforce a closet item limit per membership tier (values in Section 4.2 configuration table). When a Free-tier user reaches their limit, the system will block new item saves and display an upgrade prompt, without discarding the in-progress upload from the review draft.

### 3.3 Home Dashboard & Outfit Generator

3.3.1 The Home Dashboard will display current weather (via Open-Meteo API), a "Today's Outfit" AI suggestion, wardrobe stats, community banner, and shopping banner.
3.3.2 The system will generate daily outfit suggestions based on weather, wardrobe contents, style preferences (basic + advanced), and any linked event.
&nbsp;&nbsp;3.3.2.1 Each suggestion will include `aiExplanation`, `weatherCompatibility`, `colorMatching`, `styleMatching`, `matchingScore`, and `missingItems` (with shopping/community suggestions where relevant).
3.3.3 The user will have the option to refresh outfit suggestions, subject to the AI refresh quota for their tier (Section 4.2). Refresh quota can be increased via completed Missions (Section 3.5).
3.3.4 The user will have the option to confirm an outfit as "worn," which increments `timesWorn` on each constituent item and contributes to wardrobe analytics.

### 3.4 Membership & Tiering (Free / Pro / Premium)

3.4.1 The system will support exactly three membership tiers: **Free, Pro, Premium**. These values will be implemented as new enum values in the data model (`'free' | 'pro' | 'premium'`), replacing the prior `'free' | 'premium' | 'elite'` values — this is a rebuild, not a relabeling, and requires a data migration task for any existing test/staging records.
3.4.2 Each tier will have configurable limits for: AI refresh quota (Home/Outfit Generator), closet item limit, and Virtual Try-On monthly quota (Section 4.2).
3.4.3 The user will have the option to view a tier comparison screen before upgrading.
3.4.4 The user will have the option to upgrade their tier via the Payment & Billing flow (Section 3.14).
3.4.5 The user will have the option to cancel their subscription; cancellation takes effect at the end of the current billing period (no partial-period refund unless otherwise decided [TBD]).
3.4.6 **AI Model Tiering & Routing:** the system will route every AI-touching feature call (clothing detection, image enhancement, outfit recommendation, virtual try-on, style-profile analysis) to a specific model based on the combination of (feature, user tier), per the routing table in Section 9. This routing configuration will be admin-editable via `admin_settings` without requiring an app release.
&nbsp;&nbsp;3.4.6.1 Free tier will use the lowest-cost model class for every feature.
&nbsp;&nbsp;3.4.6.2 Pro and Premium tiers will use upgraded models for outfit recommendation, image enhancement, and virtual try-on from MVP launch (no gate/threshold required, per PO decision — this differs from the original "prove-it-first" gate strategy, which now applies only to further upgrades beyond the initial Pro/Premium model tier).
&nbsp;&nbsp;3.4.6.3 If a tier-appropriate model call fails, the system will fall back to the next-lower-cost available model for that feature, will notify the user the result may be lower quality, and will NOT charge the user's quota for the fallback call.
3.4.7 The system will send renewal reminders at 7 defined milestones before expiry [inherited from v1.5, mandatory/optional status still TBD — OI-5].
3.4.8 On subscription expiry without renewal, the system will automatically downgrade the user to Free tier (never an intermediate tier), immediately re-route subsequent AI calls to Free-tier models, adjust quotas, and retain (never auto-delete) existing closet items even if over the new limit — blocking only new uploads until the user deletes items or upgrades again.

### 3.5 Missions & Rewards

3.5.1 Admin will have the option to create and configure a mission with: name, mission type, target user segment [TBD — OI-4], display window (start + optional end), reward type(s)/amount(s), and frequency — without an app release.
3.5.2 The system will display a mission to a user only when the user matches its target segment AND the current time is within its display window. Missions with no `display_end` remain visible indefinitely.
3.5.3 Supported mission types: `daily_checkin`, `watch_ad`, `survey`, `invite_friend`, `share_outfit`, plus the specific "Complete Style/Color Preference" completion condition.
&nbsp;&nbsp;3.5.3.1 "Watch Ad" missions will only credit completion if the rewarded video plays to completion; exiting early will not count.
&nbsp;&nbsp;3.5.3.2 "Complete Style/Color Preference" missions will only credit completion if all required fields are filled; partial completion does not count, and submitted data feeds the Outfit Generator (3.3) as personalization input.
&nbsp;&nbsp;3.5.3.3 "Invite Friend" mission will use a **referral link** mechanism: each user receives a unique `referralCode`/link to share; completion credits when a referred user registers via that link. **This requires new data model scope**: `referralCode` field on `users`, and a new `referrals` collection tracking `referrerId`, `referredUserId`, `status` (`pending`/`completed`), and `createdAt`. Exact completion trigger (referred user's mere registration vs. registration + onboarding completion) remains [TBD].
3.5.4 The system will award XP, badges, and/or bonus AI quota (refresh and/or try-on quota) per the exact amount configured for that specific mission — not a shared default across all missions.
&nbsp;&nbsp;3.5.4.1 Bonus Virtual Try-On quota earned via missions stacks on top of the tier's base monthly allowance (Section 3.4.2), consistent with the PO's stated design for Free-tier try-on access.
3.5.5 The user will have the option to track a daily streak; one-time missions do not reset and complete only once per account.

### 3.6 Notifications

3.6.1 The system will support 5 notification types: `event`, `ai`, `mission`, `community`, `membership`.
3.6.2 The user will have the option to manage notification preferences per type/channel.
3.6.3 The system will send notifications for mission completion/reward, event reminders, AI processing completion, community activity (new message, offer, listing approval/rejection), and membership lifecycle events (renewal reminder, expiry, downgrade).

### 3.7 Admin & AI Cost Monitoring

3.7.1 Admin will have the option to view an AI cost dashboard showing cost-per-user and cost-per-feature, broken down by tier and model (sourced from `ai_logs.modelUsed` + `ai_logs.costEstimate` — costEstimate is a NEW required field on this collection, see Section 9).
3.7.2 The system will alert Admin when AI cost trends exceed a configured threshold. [TBD — exact threshold]
3.7.3 Admin will have the option to view the AI tag-correction-rate trend (how often users manually correct AI-suggested tags), as the primary signal for further model-upgrade decisions beyond the initial MVP tiering.
3.7.4 Admin will have the option to view the general Analytics Dashboard: total users, active users, membership conversion %, daily AI usage.

### 3.8 Fashion Knowledge Base & Trend Learning

3.8.1 The Fashion Knowledge Base will be seeded by AI research and will require mandatory human review before any production deployment — no auto-publish path exists anywhere in the system.
3.8.2 The system will run a Weekly Trend Monitoring Job (cron cadence: weekly, confirmed unchanged per PO decision) using Gemini Grounding with Google Search to surface candidate trend entries.
3.8.3 The system will detect correction patterns (from 3.7.3) to flag candidate Fashion Knowledge Base enrichments for Admin review.
3.8.4 Admin will have the option to approve, edit, or reject Fashion Knowledge Base updates before they affect production tagging/recommendation behavior.

### 3.9 Virtual Try-On *(NEW — promoted to MVP Must Have)*

3.9.1 The user will have the option to generate a virtual try-on image by selecting an outfit (own or AI-recommended), uploading/selecting a personal photo, and choosing a scene from: beach, mountain, urban, party, casual, office.
3.9.2 The system will enforce a monthly Virtual Try-On quota by tier:
&nbsp;&nbsp;3.9.2.1 **Free: 2 generations per calendar month, resetting on the 1st day of each month** (PO-confirmed), increasable via completed Missions (3.5.4.1).
&nbsp;&nbsp;3.9.2.2 **Pro/Premium: higher monthly allowance** [TBD — exact numbers, see Section 4.2 placeholder].
3.9.3 On quota exhaustion, the system will display: "Bạn đã dùng hết lượt thử đồ miễn phí tháng này. Hoàn thành nhiệm vụ để nhận thêm lượt, hoặc nâng cấp Pro." and block generation until quota resets or is topped up.
3.9.4 The system will NOT deduct quota on a failed/errored generation attempt.
3.9.5 The user will have the option to save the generated image to their device or share it via the native share sheet.
3.9.6 The user will have the option to save the underlying outfit (used in the try-on) to their Outfit Library (Section 3.15) directly from the try-on result screen.

### 3.10 Event Planner *(NEW — promoted to MVP Must Have)*

3.10.1 The user will have the option to create an event with: name, date, location, event type (wedding/party/work/date/travel/casual/formal/other), dress code, weather style, and mood.
3.10.2 The system will generate AI outfit suggestions tailored to the event's dress code and context, using the same Outfit Generator engine (3.3) with event context as additional input.
3.10.3 The user will have the option to link one or more saved outfits to an event (`linkedOutfitIds`).
3.10.4 The system will send event reminder notifications (type `event`, Section 3.6) at **three lead times before the event**: **1 day before**, **12 hours before**, and **4 hours before** the event's scheduled date/time. All three fire independently (not mutually exclusive) unless the user has disabled event notifications entirely (Section 3.6.2).
3.10.5 *(NEW — v2.2, Story 10.5, ADR-04/ADR-05)* The user will have the option to confirm an event as "worn" via a wear-confirm banner shown after the event's scheduled date/time has passed. Confirming will **bulk-increment `timesWorn`** on ALL outfits linked to that event (`linkedOutfitIds`) and on each of their constituent closet items, in a single action — this is a **second, independent trigger** for `timesWorn` alongside the existing Home Dashboard confirm-worn action (3.3.4); the system will not attempt to deduplicate between the two triggers even if they refer to the same real-world wear (accepted analytics imprecision, per PO decision).
&nbsp;&nbsp;3.10.5.1 The event wear-confirm action is bulk-only for MVP — the user confirms all linked outfits as worn together; there is no per-outfit confirmation within a single event.
&nbsp;&nbsp;3.10.5.2 Once confirmed, the confirmation is one-way (cannot be un-confirmed) and is idempotent — a duplicate confirmation request will not double-increment `timesWorn`.
&nbsp;&nbsp;3.10.5.3 The user will have the option to dismiss the wear-confirm banner without confirming; dismissal does not increment `timesWorn` and the banner will not reappear for that event.

### 3.11 Community / Marketplace ("Pass đồ") *(NEW — promoted to MVP Must Have)*

3.11.1 The user will have the option to create a listing from a closet item, with listing type (sale/trade/giveaway), price (if sale), condition, description, photos, size, location, and tags.
3.11.2 Every new listing will enter `status=pending_review` and will NOT be publicly visible until an Admin approves it.
&nbsp;&nbsp;3.11.2.1 Admin will have the option to approve or reject a listing, with an optional moderation note communicated to the seller on rejection.
3.11.3 Approved listings will be visible to authenticated users AND guests (per Section 3.16 public-read rules).
3.11.4 The user will have the option to message a seller (`marketplace_messages`) or submit a trade offer (`trade_offers`, optionally referencing one of their own closet items) on any approved listing.
3.11.5 The user will have the option to report a listing for violation; reports enter `status=open` and follow an Admin review workflow (`reviewing → resolved/dismissed`).
3.11.6 On a completed sale, the system will create a `transactions` record computing `platformFee` from `platformFeePercentage`, and will track status progression: `pending → paid → shipped → handed_over → completed` (or `cancelled`).
3.11.7 **Escrow / secured payment handling for C2C transactions is explicitly out of scope for this phase** (deferred to Phase 2, per PO decision) — the system facilitates connection and messaging only; this limitation will be disclosed to users before their first listing or purchase action.
3.11.8 Admin will have the option to view and manage all listings, reports, and transactions from the Admin CMS (Section 3.17).

### 3.12 AI Shopping Assistant & Affiliate *(NEW — promoted to MVP Must Have)*

3.12.1 The system will surface affiliate product suggestions when the Outfit Generator identifies a `missingItems` gap in the user's wardrobe relevant to a recommended outfit.
3.12.2 The user will have the option to view a dedicated Shopping screen listing affiliate products, filterable/relevant to their style profile.
3.12.3 The system will track shopping-related events (`affiliate_click`, `product_impression`, `community_item_click`) per user, tagged with `source` (ai_stylist/shopping/community) and, where applicable, the originating `recommendationId` or `outfitId`.
3.12.4 Admin will have the option to manage affiliate products (add/edit/deactivate) and view aggregate clicks, conversions, and estimated revenue (VNĐ) per product.

### 3.13 Style Profile & Advanced Style Preferences *(NEW — full MVP scope, per PO decision)*

3.13.1 On first login, the user will be routed to an initial Style Survey (Quick Style Quiz) capturing: preferred styles, favorite colors, lifestyle/occasions, fashion confidence level, gender, age group, and disliked colors.
&nbsp;&nbsp;3.13.1.1 The user will have the option to skip the initial survey; skipping still marks `hasCompletedStyleSurvey=true` with `styleSurveySkipped=true` so the user is not re-prompted every session.
3.13.2 The user will have the option to edit style preferences later from Profile ("Chỉnh sửa gu thời trang").
3.13.3 **Advanced Style Preferences are in scope for MVP** (full detail, not deferred): body shape, height (cm), weight (kg), top size, bottom size, shoe size, favorite brands, budget level, fit preference, styles to avoid, and disliked colors.
&nbsp;&nbsp;3.13.3.1 Rationale (per PO): this data is direct input to the AI Stylist prompt (Section 3.3, 3.9) and materially improves outfit-recommendation and virtual-try-on relevance — it is not a "nice to have" personalization layer.
3.13.4 The system will calculate and display a `styleProfileCompletionPercent` to encourage full profile completion (tie-in with Missions 3.5.3.2).
3.13.5 The system will call `POST /api/ai/style-profile/analyze` to generate a structured `StyleProfile` (summary, primary styles, preferred colors, recommendations) — this AI call is also subject to AI Model Routing (Section 9) by tier.
3.13.6 Admin will have the option to filter the Users list by style survey completion status, preferred style, favorite color, and budget level (already implemented in Admin Users page — retained as-is).

### 3.14 Payment & Billing

3.14.1 The system will support VNPay and MoMo as the **priority/launch payment methods**.
3.14.2 Apple Pay and Google Pay support is deferred to **Phase 1.1**, pending App Store/Play Console merchant setup — UI and constants may exist in code ahead of this, but these methods will not be presented as active options to users until Phase 1.1.
3.14.3 The user will have the option to select a payment method and initiate a Membership upgrade transaction from the Payment Prepare screen.
3.14.4 On payment success, the system will update the user's `plan`, create/update the `subscriptions` record, and immediately apply the new AI Model Routing tier (Section 3.4.6).
3.14.5 On payment failure or cancellation, the system will make no plan change and will return the user to the Membership screen with a clear, non-ambiguous failure message.
3.14.6 Admin will have the option to view payment/financial reports (Admin > Payments & Finance) and individual transaction records (Admin > Transactions).

### 3.15 Outfit Library Management *(NEW)*

3.15.1 The user will have the option to view a list of all saved outfits.
3.15.2 The user will have the option to view outfit detail: constituent items, AI explanation, weather/color/style matching, and matching score.
3.15.3 The user will have the option to mark an outfit as favorite (`isFavorite`) or saved (`isSaved`).
3.15.4 The user will have the option to hide or remove an outfit (`status: active/hidden/removed`) without deleting the underlying closet items.
3.15.5 The system will track `timesWorn` per outfit, incremented via the "Confirm as worn" action (3.3.4).

### 3.16 Guest / Public Browsing Mode *(NEW)*

3.16.1 A user who has not authenticated will have the option to browse the app in Guest mode, with read access limited to: active `plan_limits`, active `missions`, published `trends`, active `affiliate_products`, and `approved` `listings`.
3.16.2 Any action requiring authentication (upload, save, message, offer, mission completion, AI generation) will trigger a sign-in prompt (`GuestAuthModal`) rather than failing silently.
3.16.3 On successful sign-in from a guest session, the user will be routed to continue their prior action where feasible (e.g., resume viewing the listing they tapped) rather than restarting at Home.

### 3.17 Admin CMS *(Expanded scope vs. v1.5 Epic 7)*

The Admin CMS will provide role-based (RBAC) management across the following areas, each with list/filter/detail/CRUD capability as applicable:

3.17.1 **Users** — view/filter by plan, style survey status, status (active/suspended/banned); Admin will have the option to suspend/activate a user, reset plan, and adjust AI quota manually.
3.17.2 **Admin Users** — RBAC management of admin accounts and their permission roles.
3.17.3 **Membership** — manage `plan_limits` (per-tier quotas) and view `subscriptions` (MRR/churn source data).
3.17.4 **Missions** — CRUD missions per Section 3.5.1; view completion rate and claims count.
3.17.5 **Community** — moderate `listings` (Section 3.11.2).
3.17.6 **Moderation** — review `listing_reports` and other user reports.
3.17.7 **Notifications** — manage push/notification templates and scheduling.
3.17.8 **CMS Content** — manage `cms_content` entries: home banners, onboarding slides, FAQ, legal pages, seasonal collections; each with `draft/published/archived` status.
3.17.9 **Trends** — manage `trends` (Fashion Knowledge Base output, Section 3.8).
3.17.10 **Affiliate** — manage affiliate products and view clicks/conversions (Section 3.12.4).
3.17.11 **Transactions** — view/manage marketplace transactions (Section 3.11.6).
3.17.12 **Payments** — financial reporting (Section 3.14.6).
3.17.13 **Security & Audit** — view `admin_logs`: login events, failed logins, admin actions, and any user status/quota/membership changes, for audit trail purposes.
3.17.14 **Support** — manage `support_tickets` (open/in_progress/resolved/closed).
3.17.15 **Outfits** — curate/moderate user-generated outfits (saves/wears visibility for Admin).

## 8. References — Glossary

- **Wardro** AKA "Your Closet" (codebase name), "Diện" (earlier naming candidate) — the product name; final brand pending trademark resolution (OI-1).
- **Wardrobe Graph** — the accumulated, structured dataset of a user's digitized closet items and their relationships (co-worn, style-matched), treated as the product's core competitive moat.
- **AI Model Tiering / Routing** — the strategy and technical mechanism of selecting a different underlying AI model per (feature, membership tier) combination to balance cost and quality.
- **Fashion Knowledge Base (FKB)** — the curated, human-reviewed taxonomy and reference dataset used to ground AI clothing detection and trend outputs.
- **Pass đồ** — Vietnamese colloquial term for "passing along clothes," the product's name for its Community/Marketplace resale/trade/giveaway feature.
- **North Star Metric** — Weekly Outfits Worn, the primary product health metric (inherited from Product Vision v2.0).
- **Tier** — one of Free, Pro, or Premium; determines feature limits and AI model quality.
- **AiResult** — the internal response envelope for any AI call, carrying `source` (real/mock), `quotaChargeEligible`, and `quotaManagedByBackend` flags.
- **Guest Mode** — unauthenticated browsing state with read-only access to public-marked data.
- **Escrow** — secured, platform-held payment settlement for a transaction; explicitly out of scope for Community/Marketplace in this phase (Section 3.11.7).
- **GMV** — Gross Merchandise Value; total value of transactions flowing through the Community/Marketplace feature.
- **Nghị định 13/2023** — Vietnam's personal data protection decree, the compliance basis for Section 3.1.7 and the Product Vision's data-sale prohibition.

## 9. Appendix — AI Model Routing Table (v2.2 — supersedes v2.1 placeholder table; narrows but does not fully close OI-6)

*Updated during Solution Architecture: `clothing_enhance` and `virtual_tryon` both require multi-reference image editing (accepting existing images as input, not generating from text alone), which rules out pure text-to-image models like the Imagen 4 family — Imagen 4 does not accept reference images. The Nano Banana family (Gemini native image generation/editing) is the only model family confirmed to support this. `clothing_detection`, `outfit_recommend`, and `style_profile_analyze` are text/vision-reasoning only and are unaffected by this constraint.*

| Feature | Free | Pro | Premium |
|---|---|---|---|
| `clothing_detection` (attribute extraction) | Flash-Lite class (text/vision, no image-gen cost) | Same — no quality benefit to upgrading this specific feature | Same |
| `clothing_enhance` (image standardization) | Nano Banana (legacy, `gemini-2.5-flash-image`) — cheapest editing-capable model, 1 candidate, routed via **Batch API** where possible (1.3.6) | Nano Banana 2 — 2–3 candidates, higher fidelity | Nano Banana 2 or Pro — 3+ candidates, best fidelity |
| `outfit_recommend` (Home + Event, text/reasoning only) | Flash-Lite + rule-based assist to reduce reliance on expensive calls | Flash class + full style profile input | Flash/Pro class ("AI Stylist nâng cao"), deeper explanation, full advanced-preferences input |
| `virtual_tryon` (image fusion — closet item + user face + scene) | Nano Banana (legacy) — **capped at 2/calendar month (fixed, resets 1st of month)**, standard quality, may include watermark, real-time/synchronous (not Batch-eligible) | Nano Banana 2 — faster, better color/character consistency, monthly quota per Section 4.2 | Nano Banana 2 or Pro — best quality, justifies premium pricing, high/unlimited quota |
| `style_profile_analyze` | Flash-Lite, runs once on survey completion | Flash class, full advanced-preferences input | Flash/Pro class |

**Fallback rule (applies to all rows):** on primary model failure, fall back to the next-lower-cost model for the same feature; do not charge user quota for a fallback-served result; log `modelUsed` and `fallbackUsed: true` to `ai_logs` for cost-monitoring visibility (Section 3.7.1).

**Remaining OI-6 scope (narrowed, not closed):** the model *family* is now confirmed (Nano Banana legacy vs. Nano Banana 2, vs. Flash-Lite/Flash/Pro for text-only features) — only the exact production `modelId` strings and Nano Banana 2 pricing/availability confirmation from the Technical Lead remain open.

**`ai_logs` collection — new required fields (vs. current implementation):**

| Field Name | Source | Store? | Description | Purpose | Example |
|---|---|---|---|---|---|
| `modelUsed` | AI proxy response metadata | Yes | Which model actually served the request | Cost monitoring, routing audit | `gemini-flash-lite` |
| `costEstimate` | Computed by backend from provider pricing | Yes | Estimated USD/VNĐ cost of this call | Feeds Section 3.7.1 dashboard | `0.0004` |
| `fallbackUsed` | AI proxy | Yes | Whether the fallback model was used | Reliability monitoring | `false` |
| `tier` | User's plan at call time | Yes | Which tier this call was billed/routed under | Tier-level cost breakdown | `pro` |
