# Wardro V2.1.3B — Manus Runtime and Firebase-Agnostic Foundation

## Purpose

V2.1.3B makes the current Wardro core experience runnable without a Firebase project. The active runtime is selected centrally with `WARDRO_RUNTIME_MODE=manus`; Firebase remains an explicit future provider selected with `WARDRO_RUNTIME_MODE=firebase` after the Product Owner supplies an approved project and credentials.

This phase does not implement AI enhancement, virtual try-on production, payment, marketplace settlement, community redesign, weather, notification redesign, a queue platform, Redis, Kafka, a major dependency upgrade, or a fake Firebase implementation.

## Provider boundaries

| Domain | Manus development provider | Future Firebase provider |
|---|---|---|
| Auth | `runtime.ts` allowlisted identities: `manus-user-a`, `manus-user-b`, `manus-admin` | Firebase Auth ID-token verification in `authorize.ts` |
| Data | `manus-data.ts`, server-side JSON state under `WARDRO_MANUS_DATA_DIR` | Firestore through `firebase-admin.ts` |
| Storage | `manus-storage.ts`, server-controlled files under `WARDRO_MANUS_STORAGE_DIR` and HMAC capability URLs | Firebase Storage through `firebase-admin.ts` |
| AI quota/logs | Same V2.1.1 state machine persisted in the Manus data provider | Same V2.1.1 Firestore ledger in `ai_usage` and `ai_logs` |
| AI routing | Deterministic development routing identifiers; no provider billing | `admin_settings/ai_routing` plus approved server provider |

Business routes use these boundaries only at the infrastructure seam. The Firebase path remains available and is not replaced by a simulation.

## Development identity safety

The Manus server does not accept a client-controlled arbitrary UID or request-body user ID as identity. Requests use `X-Wardro-Dev-User` only to select one of the fixed, server-allowlisted development identities. The default is `manus-user-a`. Wardrobe payload ownership is still validated against the server-derived identity.

Two-user checks must use `manus-user-a` and `manus-user-b`. `manus-admin` exists only for local CMS/RBAC testing. The Manus mode is explicit and must not be enabled in a production Firebase deployment.

## Run commands

Start the backend/API:

```bash
cd admin
cp .env.example .env.local
# WARDRO_RUNTIME_MODE=manus
npm run dev
```

For a mobile web build, use:

```bash
cd mobile
# EXPO_PUBLIC_WARDRO_RUNTIME_MODE=manus
# EXPO_PUBLIC_API_BASE_URL=http://localhost:3000
# EXPO_PUBLIC_WARDRO_MANUS_USER=manus-user-a
npx expo export --platform web
npx serve dist -l 8081
```

A clean isolated runtime can use explicit directories:

```bash
WARDRO_MANUS_DATA_DIR=/tmp/wardro-manus-data \
WARDRO_MANUS_STORAGE_DIR=/tmp/wardro-manus-storage \
WARDRO_RUNTIME_MODE=manus \
  npm run dev
```

## Health contract

`GET /health` returns application status, environment, runtime mode, provider names, non-secret build SHA, demo mode, and dependency statuses for auth, data, storage, and AI. In Manus mode these dependencies are development providers; the endpoint does not initialize Firebase Admin.

The health response contains no API key, token, service-account field, or filesystem path. The build identity comes from `WARDRO_BUILD_SHA`, `GITHUB_SHA`, or the build-time `development` fallback through `next.config.ts`.

## Wardrobe flow

The live development chain is:

```text
Manus development identity
  → server upload validation
  → Manus storage capability URL
  → authenticated development AI boundary
  → quota reserve/commit/release
  → review draft in mobile
  → idempotent wardrobe persistence
  → metadata update
  → item delete and cleanup task
  → account deletion cleanup
```

The development AI response is explicitly labeled in metadata/warnings as a `manus-development` behavior. It is not a claim of real model generation and does not consume billable provider credits.

## Firebase future contract

Firebase integration is deferred because the Product Owner does not currently have a Firebase project. The future integration points are intentionally explicit:

1. Auth: replace the Manus identity selector with Firebase ID-token verification and preserve the `ApiIdentity` contract.
2. Data: route provider operations to Firestore while preserving server ownership checks, idempotency, count updates, quota transactions, and retention policy.
3. Storage: route upload, read capability, delete, and account-prefix cleanup to Firebase Storage while preserving MIME/size/signature validation and owner isolation.
4. Environment: set `WARDRO_RUNTIME_MODE=firebase` and provide Firebase-only server/mobile configuration through deployment secrets; never commit credentials.

No Firebase resources, credentials, fake Firebase objects, or security-rule bypasses are created by V2.1.3B.

## Verification

The required Manus runtime E2E is `tests/manus-runtime-e2e.mjs`. It covers health, session creation, public data reads, server upload, AI development behavior, idempotent persistence, owner CRUD, cross-user read/update/delete denial, Storage denial, successful cleanup, and account deletion. It must run against a live Manus-mode Next.js process with isolated data and storage directories.

Firebase emulator/rules suites remain valuable regression evidence for the future Firebase provider and are reported as `DEFERRED — FIREBASE NOT AVAILABLE` when an external Firebase project is required. They are not silently relabeled as Manus runtime success.
